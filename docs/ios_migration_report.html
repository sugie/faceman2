結論

NativePHP for Mobile v3 を採用し、Laravel をそのまま iPhone 上で動かす

v3 が 2026年2月に MIT ライセンスで無料化された（旧版は有料）。このアプリは外部通信を必要としない自己完結型の診断アプリなので、サーバーを一切立てずにデバイス内で完動させられる。既存の Blade / Livewire / Eloquent はほぼそのまま再利用できる。

なぜこのアプリが NativePHP 向きなのか

コードを読んだ結果、移植に有利な条件が偶然そろっていた。

  • 完全に自己完結している

    BikeFit の診断ロジック（BfWeight::getDiagnostic → getBestOne → getResultDescription）は外部 API を一切呼ばない。ログインも決済もない。つまりオフラインで完動する。

  • アセットビルドの罠がない

    layouts/app.blade.php も bikefit/index.blade.php も <style> 直書きで、Vite に依存していない。public/build/ も存在しない。ここでハマる要素がない。

  • 問診データが migration に入っている

    これが効く。NativePHP は「アプリ起動のたびに必要に応じて migration を実行」する仕様なので、2025_10_26_010000_seed_bikefit.php の質問・選択肢・重み付けが初回起動時に自動で入る。seeder を別途動かす仕組みを作らなくてよい。

  • 規模が小さい

    合計 2,700 行程度。詰まったときに方式を捨てて別ルートへ切り替えても傷が浅い。

移植の障害

NativePHP は SQLite のみ対応で、MySQL は使えない。「アプリは逆コンパイルできるので DB 認証情報を埋め込ませない」という意図的な設計判断による。この前提で既存コードを全件当たった結果が次のとおり。

MySQL 依存箇所の SQLite 互換性
箇所 内容 SQLite での結果
bikefit_schema.php:23, 38
tyukosyaerabi_schema.php:23, 38		 DB::statement("ALTER TABLE … COMMENT …") × 4 要修正 エラーになる。唯一の実害
各 migration ->comment('匿名ユーザー識別ID') 等 無害 無視されるだけ
各 migration enum('license', […]) 等 動作 Laravel が varchar + check に変換

.env SESSION_DRIVER=file によるセッション駆動ウィザード 動作 1端末1ユーザーなので問題なし

修正は 4 箇所のみ。ドライバ判定で囲めば、Docker 側の MySQL 開発環境を壊さずに両立できる。

// database/migrations/2025_10_26_000000_create_bikefit_schema.php
if (DB::getDriverName() === 'mysql') {
    DB::statement("ALTER TABLE bf_users COMMENT 'Bike fit users'");
}

Docker 一式は iOS ビルドには不要。

fm2_httpd（6344）/ fm2_mysql（6342）/ fm2_phpmyadmin（6343）/ fm2_redis（6345）は Windows 側の開発環境としてそのまま残す。Mac 側の iOS ビルドでは一切使わない。

Capacitor によるラッパーは、Apple の「Safari で見るのと十分に違わない体験のアプリは App Store にふさわしくない」というガイドライン 4.2 に真正面から当たる。逆に NativePHP はコンテンツがアプリに同梱されオフライン動作するため、この点で有利。ただしゼロリスクではない。

Mac 側の実行手順

環境要件（公式）

要件 内容 現状
ハードウェア Apple Silicon M1 以降の Mac 充足 M4
Xcode 16.0 以降 + Command Line Tools 要導入
パッケージ管理 Homebrew, CocoaPods 要導入
PHP 8.3 以上 対応可 "php": "^8.2" のため composer.json の変更不要
Laravel 11 以上 充足 Laravel 12
Apple Developer
Program（$99/年）		 シミュレータ動作確認には不要。実機テスト・App Store 配信・プッシュ通知で必要 要判断

手順

  1. Windows 側で SQLite 互換化を済ませ、push する

    DB::statement の 4 行をドライバ判定で囲む。Mac に渡る前に潰しておくと、向こうでの初回ビルドが素直に通る。

  2. Mac に Xcode と周辺ツールを入れる

    xcode-select --install
brew install cocoapods

  3. クローンして依存を解決する

    .env は gitignore されているためクローンには含まれない。Mac 側で新規に作成する必要がある。

    git clone git@github.com:sugie/faceman2.git
cd faceman2
composer install

  4. NativePHP を導入する

    .env に NATIVEPHP_APP_ID=com.sugie.faceman2 を追記してから installer を走らせる。

    composer require nativephp/mobile
php artisan native:install

  5. iOS シミュレータで起動する

    ここまで Apple Developer 登録なしで到達できる。

    php artisan native:run

最初のマイルストーン

シミュレータ上で /bikefit の診断フローが最初の質問から結果表示まで一周すること。ここが通れば、方式選択が正しかったことの証明になる。

次のアクションと未決事項

Windows 側（現時点）で先に済ませておくと、Mac での作業が楽になるものが 2 つある。

  • SQLite 互換化

    DB::statement の 4 行をドライバ判定で囲む。Docker の MySQL 環境は壊さない形で。着手可能。

  • .env の扱いを決める

    .env は gitignore のため Mac のクローンには来ない。NativePHP 用の設定値も含め、Mac 側で何を書くべきかを控えておく必要がある。

判断が必要な点：App Store 公開を目指すか、自分の iPhone で動けば十分か。

前者なら Apple Developer Program の登録（$99/年）とガイドライン 4.2 対策（ネイティブ機能の追加）を計画に織り込む必要がある。後者ならシミュレータと実機デバッグで完結し、費用も期間も大幅に軽くなる。ここが決まると以降の設計方針が変わる。
